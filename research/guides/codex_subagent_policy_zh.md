# Codex Subagent 启用策略与模型分配规范

## 1. 目的与适用范围

- 本规范用于约束 Codex 在本仓库中的 `subagent` 启用策略、模型强度分配和协作边界。
- 目标是在不牺牲正确性的前提下，用“积极但保守”策略降低主 agent token 消耗和主路径等待时间，并把可并行的探索、文档编辑、局部实现或验证任务拆分给合适强度的模型。
- 本规范不修改 `C:\Users\荀冢小宝宝\.codex\config.toml`；实际执行仍服从更高优先级的系统、运行时和会话级规则。

## 2. 默认策略：积极但保守

- 当任务可清晰拆分、低上下文、可并行推进且不阻塞当前关键路径时，默认优先考虑启用 `subagent`。
- 主 agent 默认保留当前关键路径、最终判断、diff review、验收验证和用户最终答复。
- `subagent` 更积极承担跨文件查证、状态汇总、路径定位、文档编辑、报告同步、runbook 更新、单文件局部实现和独立验证。
- 简单任务仍可本地完成；但跨 2 个及以上文件的查证或边界清晰的文档/代码小改，默认应考虑委派。

## 3. 复杂度分级与模型映射

| 复杂度 | 典型任务 | 启用策略 | 推荐模型 | 推荐 reasoning effort |
| --- | --- | --- | --- | --- |
| 简单 | 简短问答、一步检查、小重命名 | 通常不启用 `subagent`，主 agent 直接完成 | - | `low` / `medium` |
| 中等 | 跨文件搜索、状态核对、来源归因、有限文档整理 | 默认启用 `1` 个 `explorer`，除非本地 1-2 次读取即可完成 | `gpt-5.4-mini` | `low` |
| 中等实现 | 独立文档更新、报告同步、runbook 补充、单文件局部脚本改动 | 默认启用 `1` 个 `worker`，必须声明独占文件范围 | 文档用 `gpt-5.4-mini`；代码用 `gpt-5.4-mini`，更大的局部代码改动用 `gpt-5.4` | `medium` |
| 复杂 / 高风险 | 跨模块设计、歧义较大的调试、高风险重构、关键正确性验证 | 主 agent 保持主线，按独立模块或验证流启用多个 `subagent` | 关键流优先 `gpt-5.4`；受限子任务可用 `gpt-5.4-mini`；轻量搜索用 `gpt-5.4-mini` | `high` / `xhigh`（关键流），`medium`（受限子任务） |

### 模型选择细则

- `gpt-5.4-mini`：轻量探索、代码搜索、只读分析、文档同步、报告小节更新、很小且隔离的改动。
- `gpt-5.4-mini` / `gpt-5.4`：常规实现、普通调试、局部测试修复、边界清晰的脚本工作；任务较小且可独立收敛时用 `gpt-5.4-mini`，更大的局部代码改动用 `gpt-5.4`。
- `gpt-5.4`：跨模块设计、歧义较大的问题定位、高风险改动、关键验收或独立审查。

模型卫生说明：不要在本规范中推荐已弃用、已迁移或不再作为当前默认的模型 id；优先维护 `gpt-5.4-mini`、`gpt-5.4` 和 `gpt-5.5` 的推荐口径。

## 4. 何时启用，何时不启用

### 适合启用 `subagent`

- 主 agent 可以继续推进主线，同时把旁路搜索、局部验证或独立实现并行出去。
- 子任务边界清楚，输入、输出和完成标准可以一次性说清楚。
- 任务可以按目录、模块或文件拆开，多个代理之间不会争抢同一写入范围。
- 需要一个独立视角做事实收集、关键验证或风险复核。
- 文档编辑、报告同步、runbook 补充可以按文件或章节独占时。
- 单文件脚本 guard、plan-only 输出、错误信息、只读审计增强可以独占文件时。

### 不适合启用 `subagent`

- 当前下一步就是主线关键阻塞，主 agent 立刻需要该结果才能继续。
- 任务过小，delegation 的沟通和等待成本高于本地执行成本。
- 子任务边界模糊，强依赖当前上下文，或需要频繁来回澄清。
- 多个子任务很可能改到同一文件、同一接口或同一逻辑块，容易引入冲突。

## 5. 并行拆分与协作边界

- 每个 `subagent` 都必须有明确职责、预期输出和文件或模块 ownership。
- 多个 `subagent` 并行写入时，优先保证写入范围互不重叠；如无法避免，改由主 agent 保留该部分实现。
- 读多写少的事实收集优先交给 explorer 风格的 `subagent`；带有明确交付物的局部实现或验证优先交给 worker 风格的 `subagent`。
- 主 agent 在 `subagent` 运行期间继续处理非重叠工作，不因“等结果”而空转；只有在下一步确实被阻塞时才等待。
- 主 agent 负责统一集成、冲突处理、接口对齐、最终验证和面向用户的交付说明。
- worker 产物只算候选补丁；主 agent review diff 并跑必要验证后，才可纳入最终结论。
- worker 不得改写未授权文件，不得 revert 他人改动，不得把 proxy / QC 产物升级为正式 synthetic / geometry 证据。

## 6. 典型示例

- “解释一个脚本做什么”或“改一个 Markdown 标题”：不开 `subagent`。
- “主 agent 正在修一个局部 bug，同时需要确认调用链或配置入口”：可并行启用 `1` 个轻量探索 `subagent`。
- “同步当前 blocker 到单个 report 或 handoff 小节”：可启用 `1` 个轻量 worker，独占该 Markdown 文件或章节。
- “给单个 orchestrator 补 plan-only readiness 字段”：可启用 `1` 个 worker，独占该脚本文件，要求返回验证命令。
- “跨多个模块排查问题，并补独立验证”：主 agent 走主线，按模块搜索、局部实现、验证拆给多个 `subagent`，并按风险选择 `gpt-5.4` 或常规模型。

## 7. 落地检查

- 启用前确认：该子任务是否能独立完成、是否能并行推进、是否真的节省主 agent token / 总时间。
- 委派时必须写清：任务目标、独占文件范围、禁止事项、验证命令、返回格式。
- 完成后确认：ownership 是否清晰、接口是否兼容、diff 是否符合边界、是否需要补文档或 smoke check 说明。
- 若实际任务与本规范冲突，以更高优先级的系统或运行时规则为准，并由主 agent 在最终交付时显式说明采用了哪条覆盖规则。

## 8. 推荐委派模板

文档 worker：

```text
子任务：更新 research 报告中的当前 blocker / 下一步命令小节。
文件范围：只允许修改 research/reports/<file>.md。
约束：不得新增完成声明；不得把 proxy 写成 synthetic；只同步已验证命令输出。
输出：修改摘要 + 文件路径 + 需要主 agent 复核的 1-3 个点。
```

代码 worker：

```text
子任务：在 tools/carla_air/<script>.py 中补 plan-only readiness 字段。
文件范围：只允许修改 tools/carla_air/<script>.py。
约束：不得改变 execute 路径语义；不得写入正式输出；保持向后兼容。
验证：py_compile + 相关 plan-only 命令。
输出：变更摘要 + 验证命令 + 潜在风险。
```
